# 方案执行

一次执行两闸：先红后绿；没有本轮跑出来的命令输出，不准说做完。
修 bug / 测试红 / 意外行为：根因没查清不准改。

对用户说简体中文。提交走 `/git-commit`，本层不 commit、不跑提交闸。

## 何时用 / 跳过

**用**：实现功能、修 bug、改行为、重构、用户说「直接做」、执行 `/execute`、方案并行会话开场白、宣称做完 / 修好 / 通过之前。

**跳过**：

- 用户要求提交 / PR：走 `/git-commit`（本层不 commit）
- 纯问答、查代码、本机排障
- `require-ana/` 会议三件套：走 `.cursor/rules/require-ana.mdc`，不代替实现

配置、生成物、一次性原型、纯文案/样式、skill / rule / 文档：可跳过红绿循环，**不能**跳过收口闸。没问过用户就当必须走循环。

想「这次先写代码再补测试」= 找借口。删掉已写的实现，从失败测试重来。不许留着当参考，不许边看边改。

动 `require-ana/` 时同一批读 `.cursor/rules/require-ana.mdc` 与 `require-ana/AI-GUIDE.md`。本会话已读过则按已读内容写，不要重读。

## 本仓

KIT 按目录独立。落盘跟着现有脚本走，不引入 bun / Next / Prisma，不把 PowerShell 改写成 Python（反之亦然），除非用户点名。

| 改动 | 测试位置 | 默认验收 |
|---|---|---|
| `*.py` | 同目录 `foo_test.py`；已有 `tests/` 则 `tests/test_<name>.py` | `python -m unittest <模块>` |
| `*.ps1` | 同目录 `foo.Tests.ps1` | `Invoke-Pester -Path <文件>` |
| `*.bat` / 无框架脚本 | 计划写死的复现命令 | 该命令 exit 0 且输出对得上 |
| skill / rule / 文档 | 无单测 | `Select-String -Path <文件> -Pattern <锚点>` |

例：改 `sand_client_mode.py` → `sand_client_mode_test.py`，跑 `python -m unittest sand_client_mode_test`。

## 回合（简化过程，不简化规范）

根因、失败测试、最小改动压在 **1～3 批工具**。排障 8 步在本回合过完，不要一步一轮。文案 / 样式 / 一眼修复：跳过红绿，仍须用本轮命令（跑脚本或 Select-String）才能说做完。

没按本仓约定写 = 没做完，不能用「回合不够」跳过。

## 范围

只改用户消息或方案任务用 `@path` 点名的文件。有并行泳道时不要碰其他泳道。做完回复：diff 范围 + 验证命令全文输出。

本目录的参考文档（如 `testing-anti-patterns.md`）不是中间产物，不要搬。

## 铁律

```
根因没查清 → 不准改
没有先失败的测试 → 不准写实现
没有本轮命令输出 → 不准说做完 / 通过 / 修好
```

## 排障

修 bug、测试失败、意外行为时，先走本节，再进下面的循环。症状补丁算失败。

1. **读证据**：报错、栈、行号、退出码、本轮命令全文。不要略过 warning。
2. **复现**：能稳定复现再改。复现不了就先收集，不猜。
3. **看近因**：本轮 diff、近期提交、配置 / 环境差异。
4. **对照能跑的**：同仓里类似且正常的写法，列出每一处差异，不要假定「那无关」。
5. **定位**：坏值从哪进来，沿调用往上追到源。多层（入口 CLI → 解析 → 改文件 / 调系统命令）在边界看进出数据，先标哪一层断。
6. **一条假设**：写清「我认为 X 是根因，因为 Y」。只改一个变量验证。错了换假设，不要叠补丁。
7. **再进循环**：用失败测试钉住根因，做最小修复。
8. **连修 3 次仍坏**：停。多半是架构或耦合问题，先跟用户说，不要第 4 次盲改。

赶时间、看起来简单、已经猜过几次，更要走完上面，不要「先补一刀再说」。

## 循环

一条行为一个测试。名字说清行为。测真代码，非不得已不 mock。加 mock 或测试专用方法时先读 [testing-anti-patterns.md](testing-anti-patterns.md)。

1. **红**：写最小失败测试。按上表跑对应命令。必须是断言失败（缺功能），不是语法错误。立刻通过 = 测到了旧行为，改测试。
2. **绿**：只写让这个测试通过的最少代码。不顺手加功能、不改旁路。
3. **再跑**：本测试通过，相关旧测试也通过，输出干净。失败改实现，不改测试来迁就。
4. **重构**：只在绿之后。去重、改名、抽函数。行为不变，保持绿。
5. 下一条行为，再从红开始。

修 bug：排障查清后，先写能复现的失败测试，再改。没见过红的回归测试不算数。

### 好测试 / 坏测试

| | 好 | 坏 |
|---|---|---|
| 粒度 | 一件事；名字里有「和」就拆 | 一次测三件事 |
| 名字 | 说清行为 | `test1`、`works` |
| 对象 | 真行为 | 断言 mock 被调用了几次 |

卡住：不会测 → 先写期望 API 和断言；测试很复杂 → 设计太复杂，简化接口；必须处处 mock → 耦合过重。

## 收口闸

开口说通过 / 做完 / 修好之前：

1. 确定哪条命令能证明这句话
2. **本轮**完整跑完（不要用上一轮记忆）
3. 读完全文、看退出码、数失败
4. 输出对得上才说；对不上就报告实际状态
5. 有方案则逐条对任务，不要只说「测试过了」

有测试先跑对应栈的测试命令；脚本/文档用计划写死的命令或 `Select-String`。不要加跑本仓不存在的 `bun test` / `biome` / `typecheck`。

| 宣称 | 要有 | 不够 |
|---|---|---|
| 测试通过 | 本轮测试命令，0 失败 | 「应该过了」 |
| 脚本可用 | 入口命令 exit 0 且关键输出对得上 | 只改了文件 |
| bug 已修 | 原症状的测试 / 复现步骤通过 | 改了代码 |
| 回归测试有效 | 见过红再绿 | 测试绿过一次 |
| 需求齐了 | 对照方案逐条 | 测试绿了就算 |
| 泳道做完 | diff 落在点名文件 + 命令输出 | 会话说「成功」 |

提交不是本闸的事。

## 红灯（立刻停）

- 代码写在测试前；测试立刻绿；说不清刚才为什么红
- should / probably / 看起来行；先报喜再跑命令
- 「精神对了就行」「留着当参考」「这次例外」
- 没复现、没假设就改；一次叠多个补丁看哪个管用
- 连修 3 次仍坏还继续盲改

## 例子（修 bug）

空路径被接受：

红：`test_rejects_empty_path` → `python -m unittest …` → `expected ValueError, got None`
绿：空路径就抛错 → 再跑 → PASS
重构：多字段再抽校验。

做完才说修好，并把该命令输出放进回复。
