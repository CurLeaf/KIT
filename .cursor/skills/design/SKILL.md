# 分析与方案

先看现有代码，再给设计，用户点头后再写实现方案。不要 visual companion。

对用户说简体中文。计划正文里的路径、命令、代码保持原样。

不要 worktree、不要强制子代理流水线、不要自动 `git commit`。执行走 `/execute`（`.cursor/skills/execute/SKILL.md`）。本仓没有 git-commit skill：提交等用户明确要求。

用户说「直接做」则跳过本技能，走 `/execute`。未完成设计、用户也没给等价设计时：先做下面「分析」，不要凭空写计划。

## 本仓

KIT 是工具箱，按目录独立，不要为了统一栈去引入 bun / Next / Prisma。

| 目录或文件 | 栈 | 摸现状时对照 |
|---|---|---|
| `sand_client_mode.py` | Python CLI | 现有 argparse 子命令与同文件辅助函数 |
| `compress-wsl-disk/` | PowerShell | 脚本顶部路径常量与现有阶段 |
| `kill-port/` | bat | 现有用法，不要改成立体框架 |
| `.cursor/skills/`、`.cursor/rules/` | Cursor 约定 | 只改编目标 skill / rule |
| `require-ana/` | 会议三件套 | `.cursor/rules/require-ana.mdc` 与 `require-ana/AI-GUIDE.md` |

设计须落在现有目录与脚本约定上，不要另起架构。

## 何时用 / 跳过

**用**：新功能、改行为、有取舍的重构、用户要「分析 / 设计 / 对比方案 / 实现方案 / 计划」。

**跳过**（直接进入实现，走 `/execute`）：

- 用户说「直接做」「按这个改」「不用分析」
- 一眼能改的单文件修复、文案、配置开关
- 纯问答、查代码、本机排障
- `require-ana/` 会议三件套（`出会前清单` / `出确认表` / `出会后结论`）：走 require-ana 规则，不代替分析
- 用户要求提交：等用户点名再 commit，本层不提交

## 回合

第一批并行：相关代码 +（对上号才读）require-ana 规则或既有 skill。**本回合**写完摸现状、对比、推荐和设计。禁止先只读本 skill。等确认 = 等用户一句话。

单会话能做完、且用户没要并行方案时：**不要**写 `w<波次>-t<任务>` 会话文件，对话里写清改哪些文件即可。只有多波次或要开并行会话才写会话文件。

## 分析

1. **摸现状**：读相关文件、约定、近期改动。用现有结构，不要顺手大重构。范围过大（多个互不依赖的工具目录）时先拆开，只把第一块分析完；其余在实现方案里标成后续波次，不另开文件。动 `require-ana/` 时同一批读规则与 `AI-GUIDE.md`。
2. **澄清**：缺目的、约束或成功标准时再问。一次最多两三个相关问题；能从代码推断的不要问。选择题优于开放题。
3. **对比方案**：给 2–3 个做法，写清利弊，推荐一个并说明理由。YAGNI：砍掉当前不需要的能力。
4. **给出设计**：按复杂度伸缩（几句到一两段）。覆盖：结构与边界、关键文件、数据流、错误处理、怎么验证。边界要能独立理解、独立测。
5. **等确认**：设计写在对话里即可，不自动写 spec、不自动 commit。用户要求落盘时写到 `.superpowers/plans/YYYY-MM-DD-<topic>-design.md`，仍不提交。
6. **下一步**：用户同意设计后，写下面「实现方案」。用户说直接实现则跳过计划，走 `/execute`。

## 自检

落笔前扫一遍：有没有含糊需求、互相矛盾、范围过大、两种解释。有则当场改清楚，选一个解释写明。

## 实现方案

把已确认的设计拆成可执行任务。假定执行者熟悉编程，但不熟悉本仓路径和约定。DRY、YAGNI、TDD。

### 保存位置

写到 `.superpowers/plans/YYYY-MM-DD-<feature-name>.md`。只写文件，不提交。

### 拆任务之前

先列将创建/修改的文件，以及每个文件的职责。跟着现有结构走。文件过大且本次必须改时，可以把拆分写进计划；不要无关重构。

### 并行检查（必须）

列出任务后、写正文前，对每个任务看三样：要改的文件、接口消费/产出、能不能单独测。标波次。

- **可并行**：不写同一文件（测试也算）、不消费对方尚未产出的符号、能独立验收
- **必须串行**：共享文件、后任务吃前任务的新接口、同一模块连续 TDD

文首必须写 `**并行：**` 与 `**波次：**`。不能并行就写原因，禁止空着。波次只说明顺序，不自动开子代理、不强制 worktree。

一个任务：一份可独立验证的交付（含它需要的脚手架/文档）。评审能驳回这一块、同时通过旁边那一块，才值得拆开。

### 计划文首

```markdown
# [功能名] 实现方案

**目标：** [一句话]

**做法：** [2–3 句]

**约束：** [语言、命令、命名等，逐条写死；没有则写「无额外约束」]

**并行：** 可并行 | 不可并行
**波次：**
- 波次 1（可并行）: 任务 2、任务 3 — [为何独立]
- 波次 2（汇合）: 任务 4 — [等波次 1]
```

不可并行时波次写成一条顺序，并写原因。不要写 subagent-driven-development / executing-plans / worktree 流水线。

### 会话文件（每个任务都要，含串行波次 1）

方案正文只保留任务细节。开场白不堆在方案里，写到扁平目录，文件名必须能从**前缀看出波次**：

`.superpowers/plans/YYYY-MM-DD-<feature>/w<波次>-t<任务号>-<slug>.md`

例子：`w1-t1-extract-parser.md`、`w2-t2-cli-flag.md`、`w2-t3-ps1-progress.md`（同一波次共享 `w2-` 前缀，资源管理器里会排在一起）。

不要再套 `wave1/task1/` 子目录，也不要用只有任务号的 `01-foo.md`（看不出波次）。波次 1 / 任务 1 也必须有文件，不能因为「串行」就省略。

方案文首的「并行会话」只做索引表（会话文件路径、依赖哪几个会话、验收命令），不要再贴整段开场白。

每个会话文件必须能单独拖进新对话，并写清：

| 段 | 写死 |
|----|------|
| 依赖 | 哪些会话必须先做完；无则写「无」 |
| 执行指令 | 固定写 `/execute`，并写「按 `@.cursor/skills/execute/SKILL.md`」；不要改写成「按 execute 做」 |
| 拖入（已有） | 现有文件，一行一条仓库相对路径，给人从资源管理器拖进窗口；必须含 `.cursor/skills/execute/SKILL.md` |
| 本会话将新建 | 还不存在的路径，标明无法先拖 |
| 不要改 | 其他泳道的路径 |
| 开场白 | 可整段复制的第一条用户消息；**第一行必须是** `/execute`；含 `@` 引用 |

开场白必须按下面模板填空，禁止改写成「在本仓按 execute 做」这类暗示。第一行的 `/execute` 用来调用 execute skill，不要删、不要改成反引号包起来的 `execute`：

```
/execute

只做任务 N。先读并按 @.cursor/skills/execute/SKILL.md 执行。先读 @<方案> 与 @<本会话文件>。只改 @<本泳道已有文件>。验收：<命令> 预期 PASS。做完回 diff + 命令输出。
```

「引用」= `@` 路径。缺 `/execute`、缺 `@.cursor/skills/execute/SKILL.md`、缺引用或写「相关文件」一律不合格。已有文件既要出现在「拖入」清单，也要在开场白里 `@`。新建文件只写在「将新建」，不要假装能拖。

### 任务模板

每个任务包含：文件列表、接口（消费/产出的函数名与类型）、TDD 步骤、精确命令。改代码的步骤必须给出代码，禁止「类似 Task N」「稍后补充」「加上合适的错误处理」。

验收命令按栈写死，不要写 `bun test`：

| 栈 | 测试位置 | 验收命令 |
|---|---|---|
| Python | 同目录 `foo_test.py`（已有 `tests/` 则 `tests/test_<name>.py`） | `python -m unittest foo_test` |
| PowerShell | 同目录 `foo.Tests.ps1` | `Invoke-Pester -Path path/foo.Tests.ps1` |
| bat / 纯脚本行为 | 同目录断言脚本或直接跑入口 | 计划里写死的命令 + 预期输出 |
| skill / rule / 文档 | 无单测 | 「确认缺失 → 写入全文 → Select-String」 |

````markdown
### 任务 N: [名称]

**文件：**
- 新建: `path/to/file.py`
- 修改: `path/to/existing.py`
- 测试: `path/to/existing_test.py`

**接口：**
- 消费: [上一任务产出的签名]
- 产出: [后续任务要用的函数名、参数、返回值]

- [ ] **写失败测试**

```python
import unittest

class TestName(unittest.TestCase):
    def test_...(self):
        ...
```

- [ ] **跑测试，确认失败**

运行: `python -m unittest path.to.existing_test`
预期: FAIL（缺实现 / 断言未满足，不是语法错误）

- [ ] **最小实现**

```python
# 完整实现代码
```

- [ ] **跑测试，确认通过**

运行: `python -m unittest path.to.existing_test`
预期: PASS
````

不要在任务里加 Commit 步骤。纯文档/技能变更、且方案约束写明不新增测试时：用「确认缺失 → 写入全文 → Select-String 验收」代替红绿，仍须给出完整文件内容和精确命令。

### 写完后

自己对照设计：每条需求是否有任务、有无 TBD/TODO、前后任务的类型名是否一致。有缺口就补任务。每个任务都必须已有 `w<波次>-t<任务号>-<slug>.md` 会话文件（含波次 1），带「执行指令」、开场白以 `/execute` 起头，并 `@` execute skill 与可拖入路径。

然后告诉用户计划路径，问：本会话按此方案实现，还是先停在方案上。
